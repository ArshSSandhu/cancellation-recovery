## Core promise: retained

**Permissions.** `app/api/action/route.ts` obtains the actor from an opaque, hashed, expiring server session (`lib/auth.ts:7`), not request-supplied role/actor fields. `lib/scheduling.ts:74` requires staff for cancellation/sending/revocation and patients for acceptance/decline. At line 113, another patient’s offer is concealed with 404 before the replay branch. Patient reads at lines 149/154 are filtered by actor; staff-only openings/exclusions and audit are withheld. Database and HTTP checks exercise these boundaries, including a forged role. This is server authorization *after selecting a demo identity*; the passwordless identity picker itself is intentionally impersonation.

**Atomic move.** `lib/db.ts:12` uses one checked-out connection for BEGIN/COMMIT/ROLLBACK and obtains the transaction-scoped advisory lock. `lib/scheduling.ts:126` locks the original appointment and offered slot, checks the original is still booked with the offered version, rechecks all matching rules and slot availability, then uses the database wall clock for the final deadline check. Only then does it insert the new booking, mark the original replaced with its replacement link/version, accept the offer with the result ID, complete the waitlist entry and write the move audit. These become externally visible together at COMMIT. Any error, including the injected audit insert failure, rolls back the replacement and retains the original. The old appointment is retained as history; its slot becomes available when the transaction commits.

**Deadlines and retries.** Sending computes min(database send time + two hours, visit start − 24 hours) in SQL and refuses a passed cutoff. Acceptance checks `clock_timestamp()` after advisory/row-lock waiting and validation, immediately before its booking writes. A completed offer is replayed at line 114 after ownership checking, returning its stored replacement without another move audit, even if the deadline has since passed. A lost response can mean the transaction committed; UI wording preserves that uncertainty and asks for refresh/safe acceptance retry. No claim is made that a failed transport means the original is unchanged.

**Constraints.** `db/001_initial.sql:10` prevents overlapping slots for a clinician; line 18 onward prevents patient booking overlap, enforces one booked appointment per slot and ties appointment timestamps to the slot. Lines 37–49 enforce exclusive pending offers per opening and original appointment, accepted-result consistency and valid expiry intervals. These supplement the application checks. Eligibility, actor ownership, source-version advancement and truthful audits remain service responsibilities; arbitrary privileged SQL is not a supported scheduling integration.

**Audit consistency and privileges.** Every successful scheduling mutation and its corresponding audit insert share the same transaction. The move audit links offer, source/replacement IDs and old/new slots. Replaying does not append another move. The runtime role’s actual UPDATE/DELETE/TRUNCATE attempts on audit fail, and it cannot disable the audit trigger (`tests/booking.test.ts:267`). It is not a superuser or database/role creator. Owner-level UPDATE/DELETE also trigger the append-only protection. The owner can still change/drop/truncate storage; the application role can append invented events if its credentials are compromised. This is an application audit trail, not independently tamper-proof storage or an audit of every denied HTTP request.

## Sharing/setup defects corrected

- **Unrestricted destructive seed target:** previously `seed()` would truncate whichever database the admin URL named. `scripts/local-safety.ts` now restricts setup/seed/test targets to named loopback databases, refuses Vercel/remote hosts, and requires `RESET_FICTIONAL_DATA=1` to reset `recovery`. Query parameters that could override the apparent host/database are also refused. A real CLI invocation without the flag was refused and the clean database’s bookings/audit remained identical. Tests may reset only `recovery_test`.
- **No explicit Vercel demo boundary:** the local origin check already prevented normal HTTPS hosted mutations, but was not a complete hosted-access policy. `lib/local-demo.ts` now fails closed on Vercel for session reads, sign-in and mutations. A local production process with `VERCEL=1` returned 403 from all three routes, including when sent an otherwise valid loopback origin. This is a Vercel guard, not universal detection of all possible hosting platforms. Hosted access remains intentionally unimplemented.
- **Incomplete clean configuration:** standalone scripts previously did not load `.env.local`, and database/test scripts fixed their ports/URLs. `.env.example`, shared standalone loading, explicit test URLs and `LOCAL_POSTGRES_PORT` now make separate setup reproducible. README starts with the lockfile install, declares the tested Node/pnpm versions and separates restart from destructive reset. Environment files are ignored except the fictional example.
- **Malformed input became a generic server error:** null action bodies and malformed 36-character identifiers now produce 400 before reaching SQL. HTTP regression checks protect these cases.

No new defect was found in the exercised booking transaction or ownership path. No schema migration or architecture redesign was required.

## Shared lock: accepted prototype limitation

All `execute()` commands **and full `getState()` refreshes** acquire key 710428 in the same database. A refresh expires offers and audits those changes, then keeps the lock while reading appointments, offers, matching candidates and recent audit entries. An unrelated patient/clinician’s slow refresh can therefore block an acceptance; enough waiting work can consume pool connections or reach the five-second lock timeout. A statement timeout bounds individual SQL statements, not the whole multi-query refresh. Sign-in/session lookup, static assets and cached UI view changes do not acquire this advisory lock. Separate databases have separate lock namespaces.

The new real-database test (`tests/booking.test.ts:241`) blocks a refresh partway through its SQL after it has acquired the scheduling lock, launches acceptance on a distinct connection, and observes `pg_blocking_pids` naming the refresh as the direct blocker. Releasing it lets both complete with one correct audited move. This confirms the cost; it is not a performance benchmark. Existing deadline-after-wait coverage confirms a request that waits past expiry cannot move the booking.

For five fictional identities and one clinic, keeping this clear serialization contract is reasonable. Revisit when observed lock waits/timeouts, slow matching/large lists, more concurrent reviewers or multiple clinics justify it. A later change could shorten the locked section or separate consistent reads from expiry writes, with new race tests; the current review does not implement that redesign.
