# Proposed deployment — no resources created

Plan reviewed November 5, 2026. This is a recommendation for sharing **fictional data**, not approval for real patient information. No Vercel/Neon account, project, database, repository push, deployment or ZIP was created.

## Recommended target

Use a **private Vercel Next.js deployment plus Neon Postgres**, in nearby regions, with the existing Node runtime and `pg` transactions. For independent trials, give each reviewer a protected Vercel project/URL and a separate Neon branch/database, all using the same source. See [SHARING.md](SHARING.md) for the exact account/configuration checklist. This avoids adding tenancy logic to the prototype. Vercel now connects Postgres providers through its Marketplace rather than selling a new Vercel Postgres database. [Vercel Postgres documentation](https://vercel.com/docs/postgres), [Neon integration](https://vercel.com/marketplace/neon).

Choose Vercel Authentication with **All Deployments** protection, including production domains and generated URLs. Default Standard Protection excludes production domains. Invite named reviewers; do not assume a protected preview also protects the public production alias. This outer gate is reviewer access control, not staff/patient authentication. Inside an explicitly approved private fictional demo, reviewers could retain the clearly labeled impersonation switcher. Real independent users need real sign-in mapped to server-owned identities instead. [Deployment protection](https://vercel.com/docs/deployment-protection).

The current application deliberately refuses API access when `VERCEL` is set. It cannot be uploaded unchanged and expected to work. Do not remove that guard until the protected demo access model below has been implemented and tested.

## Changes required before deployment

1. Add an explicit hosted-fictional-demo mode behind the approved access gate, or replace impersonation with real authentication. Keep local defaults closed. Configure an exact HTTPS application origin allowlist instead of the loopback-only origin rule; validate it on mutations. Use Secure, HttpOnly, SameSite session cookies, bounded sessions and request limits. Scope preview origins deliberately; never accept arbitrary origins or trust an unvalidated forwarded host. Verify the gate on every generated and aliased deployment URL.
2. Set **runtime `DATABASE_URL` only** to a restricted application role using the provider’s pooled TLS URL. Create a separate owner/migration role and strong generated passwords. Never reuse local public credentials, and never put owner credentials, test URLs, reset flags or provider tokens in browser/public variables or the deployed runtime. Audit permissions must be rechecked using that actual runtime role.
3. Adapt migration tooling for an already-created hosted database and provider roles. Current `db:setup`/`db:seed` intentionally refuse remote hosts and assume permission to create local databases/roles. Do not bypass those safeguards with URL tricks. Run a reviewed, one-time release command with direct owner credentials to apply the SQL and least-privilege grants, outside the Vercel build. Neon documents `btree_gist`, needed by the existing exclusion constraints. [Extension support](https://neon.com/docs/extensions/btree_gist).
4. Keep `pg` and one checked-out client for each complete transaction. Use a small shared pool and add Vercel’s pool lifecycle helper before hosting; size the pool against the provider’s total connection limit. The current advisory lock is **transaction scoped**, not session scoped. Neon’s transaction pooler does not support session advisory locks. Verify our transaction lock, `SET LOCAL` timeouts and concurrency tests against the chosen pooler before release. [Neon pooling](https://neon.com/docs/connect/connection-pooling), [Vercel pool guidance](https://vercel.com/kb/guide/connection-pooling-with-functions).
5. Pin Node 24 and pnpm 11.25.0, install with the lockfile, and build with `pnpm build`. Do not start embedded Postgres, migrate, seed, run faults or reset data in a build/start hook. The compiled production app serves only the three application API routes. Configure log redaction, spend alerts and an intentional backup/export process; verify restore before treating the saved hosted demo as valuable.

## Test isolation and repeatable demos

Run database tests in CI against a disposable local Postgres 17 instance containing `recovery_test`, with `btree_gist` available and distinct admin/app roles. Existing test guards require loopback and that exact test name. Do not give CI race/fault tests credentials for the shared hosted demo. For provider compatibility, add a separate explicitly disposable Neon project/branch and a dedicated reviewed runner; the current destructive local tools should continue refusing it.

Preview deployments must have their own fictional database/branch and credentials, not the shared demo URL. Never copy a real-patient database into a preview or test branch. Run HTTP and browser smoke checks on the production build in a disposable environment before updating the shared demo. For hosted testing, adapt the local-only HTTP scripts to use the chosen access gate and HTTPS cookies; current local passing results do not establish hosted behavior.

Use an operator-only reset/recreate command, not a web button or endpoint, for repeating a hosted demonstration. Give it separate temporary credentials and an exact named target confirmation. Recreate relative-date fixtures just before a review so the offer cutoff has not passed; retain/export any prior audit history that needs keeping. A new disposable demo branch is preferable when different reviewers need independent journeys. Do not reset on deploy or on each page visit.

A custom domain is optional. None has been requested or provisioned here.

Review live limits and configure spending controls before authorizing resources.
